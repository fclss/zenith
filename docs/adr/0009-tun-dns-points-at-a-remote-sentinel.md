# TUN DNS points at a remote sentinel, not the gateway

After a TUN connect the client points systemd-resolved's `zenith` link at `1.1.1.1` rather than the TUN gateway `172.28.0.1`. sing-box's `hijack-dns` route action only intercepts *forwarded* packets that traverse the route system; packets addressed to the TUN's own address are delivered locally by the stack and never reach it, so `dig @172.28.0.1` timed out. A remote address is routed into the TUN → route system → `hijack-dns` → DNS engine. Considered: the TUN gateway (rejected: local delivery bypasses `hijack-dns`), a DNS listener on the TUN address (sing-box exposes none), leaving DNS at the router (rejected: queries leak outside the tunnel). Consequence: the sentinel IP is a fixed routing target, independent of the subscription's upstreams, and must never be an address excluded from the TUN routes.
